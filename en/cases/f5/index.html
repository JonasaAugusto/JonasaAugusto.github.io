The challenge

  • Free-form AI service was unpredictable and hard to audit and test.
  • Integrations with partner portals, each with its own rules, required fields, and review.
  • Steps of the partners' pipeline that never ran, leaving proposals stalled without anyone noticing.
  • Scattered data, with no single view of the operation.

Engineering decisions

  • Deterministic state machine instead of a free-form agent. The AI is restricted to classification and questions, under strict rules and a table of approved answers, so the flow is testable and auditable.
  • Idempotent integration. Each step runs exactly once and a retry resumes exactly at the missing step, with a block on resubmissions that the partner penalizes.
  • Partner query order and data minimization. The primary partner is queried first; the secondary one only receives the registration if the primary does not approve, and no data goes to a partner without need.
  • OCR with double reading and a tiebreak. The electricity bill is read twice and a third reading breaks any disagreement.
  • Registry lookup cross-checked with each portal's fields. From the CPF, the system queries a registry database and cross-checks the result, field by field, with what each portal requires, so what is already known is not asked again.
  • Data security. Encrypted cache, CPF never in plain text on disk, data masked on screens, and credentials kept out of the code.
  • Periodic portal reading. The portals are read automatically, and if a portal fails the system keeps the last valid reading. A watchdog reapplies the integrations after updates.
  • Operations dashboard. Flow documentation generated from the code itself, call logs, the state of credentials, portals, and WhatsApp, and an audit trail of actions.
  • MCP tools. The integrations are exposed as MCP tools, with simulation by default and explicit confirmation to write.

Quality

  • Over 320 automated tests cover every step, every deviation, and every integration.
  • Mutation tests prove that each fix is actually detected.
  • A real rehearsal in production, with nothing sent to the partners, before switching the number on.
  • Audit of the integrations against the partners' official documentation, which revealed steps that never ran: document upload, payment method, and contact registration.

Technologies

Python (FastAPI), WhatsApp through an in-house gateway, OCR with double reading, REST integrations, encrypted cache, React, Linux, MCP, pytest. Also in the earlier work: TypeScript, Node.js, BullMQ, Baileys, DeepSeek, PostgreSQL (pgvector), Redis, Blip, Playwright, Docker, nginx.

Earlier case study, complete (lead conversion and after-sales platforms)

Two platforms in production at F5 Tecnologia, both with AI agents on WhatsApp. The first converts leads: it receives the contact, runs the service with an AI agent, collects data, generates proposals through a financial partner, and registers customers in energy programs. The second handles customer relationship and after-sales: an AI agent with DeepSeek and tool calling, a rebuilt CRM dashboard, and cadence adjustments in Blip (the agent was validated in a sandbox and a staging stack on 10/23/2026, and the dashboard and Blip are in production). I worked end to end: architecture, agent, integrations, infrastructure, and reliability.

Relationship and After-sales Platform: first version (10/23/2026)

After-sales relied on manual contact and a slow legacy dashboard: newly enabled customers got no guidance about the benefits they had already paid for, and invoice notices arrived late. The goal was to build a continuous relationship layer (welcome, benefits journey, daily briefing, and billing alerts) without growing the team, and to modernize the dashboard and the Blip integration without stopping operations.

  • Architecture in 7 services with Docker Compose on an Ubuntu VPS: WhatsApp gateway (Baileys), AI agent, workers, dashboard API, PostgreSQL 16 with pgvector, and Redis (BullMQ). Only SSH and the dashboard API are exposed to the host, the WhatsApp session is encrypted with AES-256-GCM, and deploys go through GitHub Actions with a required reviewer.
  • Design decisions: deterministic rules before the model (cancellation, human request, dispute), model reasoning enabled by policy only where it pays off (average cost of US$ 0.0007 per turn), hybrid RAG with two confidence levels, and a sends table as the source of truth, with idempotency by key.
  • Over 750 automated tests and over 2,600 fuzz and attack cases, in a sandbox. Results include: 82 jailbreak and prompt-injection rounds with 0 failures, 60,000 messages from 3,000 senders through the gateway buffer with 0 lost, and 111 concurrent turns with the real DeepSeek, with a p95 of 8 s. The tests also found a ReDoS and a database pool without a timeout, both fixed.
  • Rebuilt CRM dashboard: 9-stage funnel with a single definition, data reconciled with the portals every 10 minutes (0 discrepancies across 1,960 items), first call from 73.7 s to 0.08 s with background build and ETag/304, and Blip conversation CRM mirrored in the dashboard, with Blip Desk synced in both directions.

Distributed Architecture

In an initial phase, I split the workload across 2 VPS: a light one for the webhook, AI agent, and orchestration; a dedicated one for browser automation (Playwright), which was CPU- and memory-heavy. To balance performance further, I built a self-hosted FastAPI API that offloaded part of the processing to the VPS with more memory, relieving the more limited one. Isolation removed resource contention and stabilized real-time service.

Later on, moving off the official WhatsApp channel (WABA) to unofficial numbers via Baileys changed the picture entirely: Baileys doesn't replicate the same conversation-handling and structuring architecture the official API offered. That forced a full infrastructure migration: I provisioned a third VPS and moved the entire operation there. In this new setup, the FastAPI load-balancing API stopped making sense, and that same migration period called for building an MCP tool server from scratch to close the new channel's structural gap (see section below).

What I Built

  • Generative AI agent (LLM with fallback), with per-stage structured prompt engineering, per-lead isolated context, and anti-hallucination guardrails (never confirms a result without a real API response).
  • OCR pipeline that reads customer-submitted documents (photo or PDF, including password-protected), extracts the key eligibility field, and detects unreadable images by automatically requesting resubmission.
  • 9-step state machine with per-lead isolated persistence, allowing the service to resume exactly where it left off if the conversation drops.
  • Integration with a financial partner API (pre-analysis, simulation, document upload, and async status polling) and web automation of external partner portals via Playwright.
  • Intelligent orchestration that routes each lead to the correct partner based on eligibility and location criteria, deriving the state from the ZIP code when missing.

Migration to a Tool Architecture (MCP)

Switching from the official WhatsApp channel (WABA) to unofficial numbers via Baileys took away a structural capability the official API guaranteed natively: a standardized way to organize and interpret the conversation flow. Without it, the agent risked "faking" that it had executed actions internally, without actually completing the registration.

The solution was to build an MCP (Model Context Protocol) server from scratch, rebuilding the entire funnel as a set of tools the agent itself calls during the conversation, in the same turn it decides to act. Each tool (coverage check, data collection, proposal creation, simulation, offer selection, finalization) executes against the partner's real API and returns the result immediately, reusing the lead's phone session, independent of the conversation-structuring capability only the official WhatsApp API guaranteed.

The safety lock lives in code, not in the conversation: finalizing registration only executes with the lead's explicit confirmation. If the agent tries to complete it alone, the system blocks the call.

Production Failure Audit & Fixes

  • Incomplete data extraction: the agent read the customer's document but wasn't capturing a key eligibility field. Coverage rose from 2% to 91%, including 12 months of history so partners could decide on the average rather than a single month.
  • Customers rejected for no real reason: an entire segment was blocked when only one specific condition actually restricted that profile; a misreading identified customers from two regions as belonging to a supplier with suspended credit, wrongly blocking 34 customers; and a credit block stayed active even after its root cause was fixed, denying an already-approved high-value proposal.
  • 142 registrations silently stuck: when a lead gave only a first name, the partner required a full name and the proposal was never created, with no one asking for the missing data. Fixed by extracting the full name directly from the customer's document (printed on it) and, when missing, asking for it explicitly.
  • Agent communication: eliminated unconfirmed-cause promises, denials announced before the cause was known, excessive emoji use (risk of WhatsApp flagging as spam), and form-style questions. I also implemented a context-cleanup routine to stop the agent repeating incorrect information already fixed in the system but still present in the conversation history.

Business Findings

Testing the funnel with real customers, I identified a structural constraint: a specific customer profile is rejected by every partner in one segment, since their benefit doesn't stack with an equivalent government benefit, even though that profile is well accepted by the financial partner. Since a meaningful share of the base fits this profile, the real addressable market for that segment is much smaller than the raw numbers suggest, a finding brought to partner negotiations.

Problems I Solved

  • Dead webhook: an outcome webhook stopped being delivered for 4 days, freezing dozens of proposals in 'processing'. I traced it from symptom to root cause (logs, database state, polling) and built a systemd job doing active polling every 5 minutes, recovering 43 approved proposals and cutting the stuck backlog from 28 to 3 leads.
  • Race condition in human takeover: when an agent joined the conversation, the bot did not pause and both replied together. I fixed it with robust phone normalization and a state re-check immediately before sending, making human handoff safe.
  • OCR latency: I cut OCR plus routing-decision time from 8s to 3.2s with smart caching (TTL) and request batching.

Reliability, Infra & Security

  • systemd services with auto-restart, health checks, state-sync watchdogs, and automatic token renewal (auto-refresh before expiry).
  • Configurable network egress layer to ensure reliable delivery to external services with unstable connectivity, without coupling business logic to infrastructure.
  • Throttling with exponential backoff to respect rate limits and behave as a well-mannered client of partner services.
  • Sensitive data handling per LGPD: encryption at rest, HTTPS transmission with JWT, retention policy, and context isolation between leads.
  • Observability with structured logging (JSON), a real-time dashboard, and automatic alerts (Slack/Email) for VPS health and webhook failures.

Automated sales on WhatsApp: from 43% to ~89% of registrations completed

Work from my internship at F5 Tecnologia: find out, with production data, why the automated registration was failing, and fix the causes instead of the symptoms.

Context

A reseller for a pay-TV carrier sells plans on WhatsApp with a chatbot. The bot talks to the customer and collects the data, and a robot (Selenium) fills in the proposal on the carrier's portal: package, add-ons, registration, payment, and validation. When the registration fails, the sale stops and the customer is left without an answer.

The problem

The sales team raised four complaints:

  • the bot stopped at the registration step with many customers;
  • answers to off-script questions took a long time to arrive;
  • registration was slow;
  • proposals were redone several times for no apparent reason.

The share of registrations that became a proposal was 43%, and it dropped as low as 29% in October. After the fix, in November, it reached about 89%.

Diagnosis: measure before changing anything

I cross-checked three sources: the timestamped step-by-step log of every robot run, the API request log, and the message history of the conversations. Three findings came out of it:

  • Most failures had a single cause. A safety check blocked 44 of 54 registrations because it did not recognize the item selected on the screen: the screen had changed and the code had not kept up.
  • The slow answers were not the AI's fault. The model answered in ~1.5 s. The time went into a fixed 15 s wait window, meant to gather a customer's message sent in pieces, which applied even to complete questions.
  • The redone proposals came from an old rule. It re-drew security questions that no longer existed, and cost ~49 s per registration.

What was done

  • Registration. I fixed how the selected item is recognized and removed the obsolete re-draw. Silent redos are now capped at 1.
  • Adaptive wait window. A recognized question (price, channels, installation…) closes the wait in 4 s, a complete piece of data (ZIP code, CPF, email) in 8 s, and the overall ceiling went from 15 s to 8 s. The cutoff came from data: out of 4,078 messages, only 2% had a second message from the customer between 8 and 15 s later.
  • Number porting with a different area code. I reproduced the failure live on the portal and found that the line's area code came from the registration's mobile number, not from the address. The robot now adjusts the area code and, if the carrier refuses, moves on with a new number instead of getting stuck. In the chatbot, the customer now confirms the number they typed and is told when the porting cannot go through.
  • Add-ons by payment method. The item required by each payment method is now checked before the others, and a failure now saves full evidence (a screenshot and the list on the screen) for diagnosis.

November: diagnosing a conversion drop with a control group

Measuring before and after by cohort, with the human team (which does not use the robot) as a control group, I showed that the drop came from a change in the carrier's policy: from 11/10/2026, almost every CPF started going to identity confirmation by document (from ~30% to ~84%), and both fronts fell the same night.

On our side:

  • Email check before registration (misspelled domain, email belonging to another CPF), with the link sent by SMS when the email does not match.
  • The robot stopped clicking “Send” on top of the carrier's automatic link.
  • Flexible ZIP code, with a search by street and city (an invalid ZIP code caused 120 of 151 closed conversations).
  • An explanation of why the CPF is asked for.
  • An option to go back to the summary.
  • “I did not receive the link”: the robot redoes it and resends it automatically.
  • Dashboard: the “Waiting” stage now shows “arrived” and “is there today”. The carrier cancels stalled proposals after ~4.5 days, and the daily number “shrank”; by the correct criterion, conversion was stable: 15.6% → 14.8%.
  • Tests: the suite for the robot and the rules went from 2,300 to over 2,500.

How I worked

  • Root cause, not a patch. Each fix applies to the whole flow and is locked in by automated tests (more than 2,500 in the suite for the robot and the rules).
  • Live proof. I reproduced the failures on the real portal, with test data, before stating the cause.
  • Safe changes in production. Isolated commits, the chatbot flow validator passing with no failures before publishing, a restart without taking the API down, and a check of what was actually published.
  • Decisions backed by data. The time cutoffs (4 s, 8 s) came from the real message history, not from a guess.

After-sales agent: rebuild and mega test

After a requirements meeting (11/13/2026), I rebuilt the relationship and after-sales agent as a 100% autonomous assistant. The first version, validated on 10/23/2026, is in the earlier case study, above.

The 6-month journey after the sale

Welcome, benefit activation, programming based on the customer's taste, billing, monthly satisfaction and retention. The billing texts are fixed and approved, never rewritten by the AI.

Reading the customer's tone

The agent reads formality, mood and irritation. It uses “sir” or “ma'am” with formal customers, uses emoji only if the customer does, and does not mistake affection (“my love”, “my girl”) for flirting.

Guardrails in code, with tests

  • No fact without a source (channel, schedule, price).
  • The amount quoted comes only from the customer's record or invoice.
  • It does not confirm what the customer has not confirmed.
  • A maximum message frequency.
  • A pause after 3 messages with no reply, keeping only billing.

Sandbox with time travel

A simulated customer, manual conversation, a “next message” button, advancing by days and months, and approval and editing of each text in the bubble itself.

CRM dashboard

New areas: Indicators, Conversations, Sandbox and Corrections. Corrections is a table with the finding, the description, the solution and the retest of each fix, with search and filters.

Mega test: 100 conversations per round, 17 rounds

Each round has 100 conversations with 10 personas (synthetic profiles and anonymized profiles): a customer AI talks to the real agent, 10 LLM judges evaluate it, and an automatic consolidator merges the result. The production gate is ≥95% and 0 critical failures.

Quality: over 6,000 automated tests and a 180-day journey simulator (15 scenarios, 0 violations).

Engineering findings

  • The real holiday of the next day postponed every message in the sandbox. The calendar is now evaluated on the customer's virtual clock.
  • The week was counted on the recorded date, not the virtual one, and let 6 messages out in a week with a cap of 5.
  • “Tá caro, não? Tô pensando em cancelar” (“Pricey, isn't it? I'm thinking of canceling”) was read as a negation. Now negation only counts inside the sentence.
  • The battery run at night produced false defects. With a fixed virtual clock, it runs at any time.

Technologies

Python (FastAPI), DeepSeek, Blip, WhatsApp, pytest, Vitest, LLM judges (automatic evaluation) and Claude Code with parallel agents (development orchestration).

How the work was run

  • Development orchestration with AI. A coordinating session plans, integrates and reports; parallel agents (different models for planning and for development) work in separate worktrees, with merges in waves.
  • State in a file. The state of the work always lives in a file, so it can resume after a crash or a limit.
  • Root cause, not a patch. Every fix applies to the whole class of the defect, with a test that locks the class.
  • Protected production. Changes stay as drafts until approved, and nothing is announced to the customer before it is live.
  • Transparency. A decisions document, a status deck, a corrections tab in the dashboard and a living case study, reviewed in full with each update.

Lessons

  • A replaced decision is swapped in place, never stacked.
  • A rule in code, with a test, is worth more than an instruction in the prompt.
  • Where risk is high, fixed text instead of the model.
  • An LLM judge has variance: the gate looks at critical failures over more than one round and with varied scenarios. Two identical rounds scored 99; the same battery on other days of the week found 2 critical failures.
  • A vendor's documentation does not replace testing.
