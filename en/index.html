What I did
A Python orchestrator (SQLite, GitHub Actions) that drives the official CLIs with the user's own logins, with no API keys. The queue and reset times live in SQLite, so pending work resumes where it stopped. Usage is measured with counters only, without reading conversations. Publishing requires the human to type the id and the commit SHA.
What broke and how I fixed it
A security audit found that the service, running as root, called git with safe.directory=* on service-owned repositories, so a repository config (hooks, fsmonitor, credential helper) could run code as root. I fixed it in v1.0.1 with a hardened git helper and root-only mirrors, and in v1.0.2 publish approvals started binding the reviewed commit SHA. Later, in v1.5.1, a failing local socket could end the process with a segmentation fault because the threads were joined after the SQLite connection was closed; the order was fixed and it now exits with an error. The known weak point left is Codex's limit message, whose format is not documented and may change; that is why detection is tolerant.
What I would do differently
I would publish to PyPI and run the full suite on Windows before calling it done. Today installation is straight from GitHub and, on Windows, CI proves only the lite mode.

How DeepSeek is used in IAprovaleDescribed from the backend code. It includes what is not ready yet.

Where it is used

  • In search: the typed sentence becomes a term or position, state(s) and the education mentioned. The model does not run the search or decide the result.
  • In Career: reads the resume and builds a structured profile, extracts a job's requirements (with a shared cache, without storing the job text) and writes the reason for "partly fits" results.
  • In exam information: reads the public notice to extract openings, dates and fees.

What it decides and what it does not

  • The list of exams comes from an external source. Filters and ranking are deterministic, tested code.
  • The result "fits", "partly fits" or "does not fit" comes from Python rules. If the model suggests another level, it is ignored.
  • Years of experience are computed in Python. Tools and numbers in the profile only stay if they appear in the resume text.

What is sent

  • In search: the typed text and, as context, education, technical course, postgraduate degree, schooling level, future education, areas of interest and city/state. Account name, e-mail, phone and CPF are not sent.
  • In Career: the resume text, up to 12,000 characters, after e-mail, phone, links and CPF are replaced by placeholders.
  • To explain a gap: the education fields of the profile and the position's requirements, without the whole resume.

Safeguards

  • The provider key lives only in the server environment. The app does not start without it, and it never goes into the repository or the front end.
  • Limits: 10 searches per minute per user; in Career, up to 17 calls or US$ 0.01 per day per account, reserved before each call.
  • In Career, a 40 s limit per call, no automatic SDK retry and at most one repeat for invalid JSON. In search, one repeat. A failure becomes a message to the user, never a 500 error.
  • The cost of each search is measured from the tokens of each attempt. The model's answer is validated against a schema, and the user's text is treated as data, not as instructions.
  • Tests with fictional data. User data never goes to development tools.

What is not ready yet

  • DeepSeek is a provider outside Brazil. Today the sending is covered by the terms of use. A specific consent on first use of Career is planned and under legal review; it does not exist yet.
  • The removal covers e-mail, phone, links and CPF. The name and address in the resume are not yet removed before sending, and the removal does not guarantee anonymization.
  • In search with the use-my-resume option on, the saved text (up to 6,000 characters) goes without that contact removal.
  • The model can be wrong. The result helps read the notice; confirmation is always in the notice and on the official portal.
Technical challengesProblems I ran into in real systems, what I did, and the result I can show.

8 GB GPU (AugustusApp)

Transcription with WhisperX large-v3 and the local LLM do not fit together in 8 GB of VRAM. I built a GPU lease, a model degradation ladder, and a probe that only accepts the LLM if it runs 100% on the GPU.

Result
One GPU owner at a time; reprocessing returns 409 instead of fighting over VRAM.

SSH terminal with 220 ms of latency

The VM terminal felt slow. I measured instead of guessing: about 221 ms RTT to the VPS in Europe and about 250 ms per keystroke even with plain ssh. I cut the app overhead with immediate output for small responses, a 6 ms tick, and a single UI dispatch, showed the RTT in the tab, and built a predictive local echo that draws each keystroke instantly and reconciles it with the server response.

Result
App overhead reduced, the network floor explained on screen, and predictive local echo shipped: keystrokes appear instantly, without waiting for the 220 ms of network.

Safe VPS backup and restore

Daily backup with restic to Backblaze B2, managed from the app: list, run now, and restore by date. A destructive restore requires confirmation, takes a safety backup first, and runs as a detached operation that survives an SSH drop.

Result
Own backup, with no paid provider backup, and restore by date without leaving the app.

Lexical RAG instead of embeddings

The bot answers technical questions from 430 curated entries. Since titles are descriptive and DeepSeek offers no embeddings, I used lexical search with IDF, synonyms, and a ranking that rewards the entry covering more of the question, at no per-query cost.

Result
In the 100-question battery with a real LLM, related entries went from 96% to 100% after the search fixes.

Connector with no automation trail

To manage the WhatsApp agents without the automation trail OpenClaw leaves for Meta, I built my own modular connector: it only runs each bot's pairing and shows the QR, keeping no session of its own, and every connection is independent.

Result
Adding a bot means editing a file, with 40 automated tests and the service listening only on loopback, with a token.

Data that matches the portals (F5)

In after-sales, the dashboard's first call took 73.7 s and it showed data diverging between portals, dashboard, and CRM. A thread that builds the data outside the request, with a ready response, ETag, and 304, plus continuous reconciliation every 10 minutes solved both problems.

Result
First call from 73.7 s to 0.08 s and 0 discrepancies across 1,960 items checked against the portals.

Case study · IAprovale

Finding the right exam or job, and keeping up with deadlines

Product built and run by me, in production. The front end is plain HTML, CSS and JavaScript, the back end is Python. This text only describes what is in the repository, the changelog and the public docs.

augustusai.com.br/iaprovale

github.com/JonasaAugusto/iaprovaledocs

The problem

  • Public-exam candidates need to find an open notice that fits their education, and the information is scattered across many sites.
  • Finding it is not enough: registration and exam dates pass, and following them by hand is easy to get wrong.
  • People looking for a job have a similar need: knowing whether a resume fits a position before applying.

What I built

  • Notice search in natural language, filtered by education and state.
  • Alerts and Following: the user follows a notice and gets reminders about registration and exam dates.
  • Career and Companies: resume upload (PDF, DOCX or TXT), job search, and, for each position of a followed notice, a verdict of fits, partly fits or does not fit, with the reason and what is missing.
  • Optional e-mail, confirmed by a code, with Brevo as the sending operator, for the daily summary and account notices.

Engineering decisions

  • Plain front end, no CDN, no bundler. HTML, CSS and JavaScript with Alpine.js in its CSP build. Alpine and pdf.js are served from the project itself, so the content security policy no longer allows a third-party script host.
  • Python only on the back end. Any new server code is Python, which keeps one language to test, deploy and maintain.
  • User data never goes to the development tools. Development uses fictional data and local copies only; production data and secrets stay out of those tools.
  • Versioned privacy policy and terms, with acceptance. Each change in the texts gets a version, such as 1.3, which describes optional e-mail, Brevo as operator and the matching international transfer.
  • Messages that say what happened. Error and confirmation messages come from a single dictionary, and alert regions stay in the page so screen readers announce them.

Quality

614/614checks passing in the automated accessibility suite
CIfront-end lint on every change to the front end
  • End-to-end tests with Playwright against a fictional API, in light and dark themes at 1280, 390 and 320 px.
  • Labels contain the visible text, targets have a minimum touch size, and breakpoints are standardized.

What I learned

  • Accessibility found real bugs: clipped labels at 390 px, a hidden alert that was never announced, and focus landing outside a dialog.
  • Fewer dependencies mean fewer surprises: removing the CDN meant tests stopped downloading Alpine and the security policy got stricter.
  • Privacy is design work, not a footer: deciding what is stored and for how long came before the screen.

What is not ready

  • Part of the latest changes appears as unpublished in the changelog (version 3.13.0).
  • Automated accessibility checks do not prove conformance; only real assistive technology confirms some points.
  • The product has no published usage numbers, so this case makes no claim about audience.

Technologies

Python, FastAPI, PostgreSQL, DeepSeek, HTML, CSS, JavaScript, Alpine.js (CSP), pdf.js, Playwright, axe, GitHub Actions, Brevo, Caddy.

Case study · AI Agents Orchestrator

Claude Code and Codex as one relay team

Personal open-source project, version 1.5.1. It drives the official codex and claude CLIs with the user's own logins, with no API keys, and nothing is published without a human approval.

github.com/JonasaAugusto/ai-agents-orchestrator

The problem

  • Anyone using Claude Code and Codex on paid subscriptions hits one limit in the middle of the work, and the task stops.
  • The two agents do not talk to each other: context and pending work are lost in the switch.
  • Delegating to an agent that writes code needs a clear checkpoint: what was really done and who authorized publishing.

The solution

The Claude leads: it plans, talks to the user, and reviews. Codex works as a second engineer on isolated branches, picks up delegated tasks and cross-reviews Claude's branches. When Claude reaches its limit, Codex takes the baton and keeps going until Claude is back.

Engineering decisions

  • Relay by limit with persistent resumption. The queue and the reset times live in SQLite. If the service or the machine restarts, pending work resumes where it stopped.
  • Measured usage, without reading conversations. Usage of both agents is counted with counters only, never with text. The target is a ratio between 0.7 and 1.4, configurable; outside it, routing moves review and test work to the other agent. The counters estimate quota use, not money.
  • Publishing bound to the SHA. The publish command shows the repository, destination and full SHA, and requires the human to type the id and the SHA in an interactive terminal. If the branch or destination changes, the approval stops being valid. The push is non-force and against the current remote base. New in 1.4.0: aao publish --pr pushes the approved SHA and opens a pull request instead of merging; it never merges.
  • MCP server that never publishes. New in 1.4.0: aao mcp exposes delegate, status, result and review to the user's agent over stdio, using only the Python standard library. Publishing stays a human approval in the CLI.
  • Parallel Codex, off by default. New in 1.4.0: with max_concurrent_codex above 1, several Codex tasks run at once only when repositories and declared files do not overlap, each with its own workspace, and merges stay serial.
  • Honest results. The task state comes from the first line of the report (completed, partial or blocked). A partial or blocked task is never shown as done, whatever the exit code.
  • Permissions chosen by the user. Codex starts restricted (own sandbox, no network, throwaway clones). On their own machine, the user can give it the same permissions as Claude. In either mode, publishing needs a human.
  • Lite mode, no root. A single user process, no systemd, on Linux, macOS and Windows, installed with pipx from GitHub. The full mode, with a privileged service and a remote channel, remains on Linux with systemd.

Verifiable results

1.4.0published version, tag v1.5.1 on GitHub
595tests collected in the suite (pytest)
CIgreen on the tag commit, on Linux, macOS and Windows, Python 3.11 to 3.14
  • CI runs the full suite on Linux and the lite mode on Linux, macOS and Windows, and also builds the packages and tests a clean installation.
  • There is a runnable example with a fake engine and a ten-minute walkthrough with output captured from a run without credentials.

What is not ready

  • The package is not on PyPI yet: installation is straight from GitHub. The release workflow is ready and stays off until the PyPI project exists.
  • On Windows, the lite mode is what CI proves; the full suite does not run there. The privileged service requires Linux with systemd.
  • Lite mode does not isolate agents from the user's account, files or Git credentials. The interactive confirmation is a workflow safeguard, not a barrier against malicious code from the same user.
  • The WhatsApp channel is an optional, unofficial extra with ban risk, tested only with fakes and not against a live account. Telegram is the recommended channel.
  • The new --pr publishing was tested only with a simulated gh, and parallel Codex only with a fake Codex, not against a live GitHub account or real Codex runs.
  • Detection of Codex's limit message is tolerant, but the format is not documented and may change.

  • Steps of the partners' pipeline that never ran, leaving proposals stalled without anyone noticing.
  • Scattered data, with no single view of the operation.

Engineering decisions

  • Deterministic state machine instead of a free-form agent. The AI is restricted to classification and questions, under strict rules and a table of approved answers, so the flow is testable and auditable.
  • Idempotent integration. Each step runs exactly once and a retry resumes exactly at the missing step, with a block on resubmissions that the partner penalizes.
  • Partner query order and data minimization. The primary partner is queried first; the secondary one only receives the registration if the primary does not approve, and no data goes to a partner without need.
  • OCR with double reading and a tiebreak. The electricity bill is read twice and a third reading breaks any disagreement.
  • Registry lookup cross-checked with each portal's fields. From the CPF, the system queries a registry database and cross-checks the result, field by field, with what each portal requires, so what is already known is not asked again.
  • Data security. Encrypted cache, CPF never in plain text on disk, data masked on screens, and credentials kept out of the code.
  • Periodic portal reading. The portals are read automatically, and if a portal fails the system keeps the last valid reading. A watchdog reapplies the integrations after updates.
  • Operations dashboard. Flow documentation generated from the code itself, call logs, the state of credentials, portals, and WhatsApp, and an audit trail of actions.
  • MCP tools. The integrations are exposed as MCP tools, with simulation by default and explicit confirmation to write.

Quality

  • Over 320 automated tests cover every step, every deviation, and every integration.
  • Mutation tests prove that each fix is actually detected.
  • A real rehearsal in production, with nothing sent to the partners, before switching the number on.
  • Audit of the integrations against the partners' official documentation, which revealed steps that never ran: document upload, payment method, and contact registration.

Python (FastAPI), WhatsApp through an in-house gateway, OCR with double reading, REST integrations, encrypted cache, React, Linux, MCP, pytest. Also in the earlier work: TypeScript, Node.js, BullMQ, Baileys, DeepSeek, PostgreSQL (pgvector), Redis, Blip, Playwright, Docker, nginx.

Distributed Architecture

In an initial phase, I split the workload across 2 VPS: a light one for the webhook, AI agent, and orchestration; a dedicated one for browser automation (Playwright), which was CPU- and memory-heavy. To balance performance further, I built a self-hosted FastAPI API that offloaded part of the processing to the VPS with more memory, relieving the more limited one. Isolation removed resource contention and stabilized real-time service.

Later on, moving off the official WhatsApp channel (WABA) to unofficial numbers via Baileys changed the picture entirely: Baileys doesn't replicate the same conversation-handling and structuring architecture the official API offered. That forced a full infrastructure migration: I provisioned a third VPS and moved the entire operation there. In this new setup, the FastAPI load-balancing API stopped making sense, and that same migration period called for building an MCP tool server from scratch to close the new channel's structural gap (see section below).

What I Built

  • Generative AI agent (LLM with fallback), with per-stage structured prompt engineering, per-lead isolated context, and anti-hallucination guardrails (never confirms a result without a real API response).
  • OCR pipeline that reads customer-submitted documents (photo or PDF, including password-protected), extracts the key eligibility field, and detects unreadable images by automatically requesting resubmission.
  • 9-step state machine with per-lead isolated persistence, allowing the service to resume exactly where it left off if the conversation drops.
  • Integration with a financial partner API (pre-analysis, simulation, document upload, and async status polling) and web automation of external partner portals via Playwright.
  • Intelligent orchestration that routes each lead to the correct partner based on eligibility and location criteria, deriving the state from the ZIP code when missing.

Migration to a Tool Architecture (MCP)

Switching from the official WhatsApp channel (WABA) to unofficial numbers via Baileys took away a structural capability the official API guaranteed natively: a standardized way to organize and interpret the conversation flow. Without it, the agent risked "faking" that it had executed actions internally, without actually completing the registration.

The solution was to build an MCP (Model Context Protocol) server from scratch, rebuilding the entire funnel as a set of tools the agent itself calls during the conversation, in the same turn it decides to act. Each tool (coverage check, data collection, proposal creation, simulation, offer selection, finalization) executes against the partner's real API and returns the result immediately, reusing the lead's phone session, independent of the conversation-structuring capability only the official WhatsApp API guaranteed.

The safety lock lives in code, not in the conversation: finalizing registration only executes with the lead's explicit confirmation. If the agent tries to complete it alone, the system blocks the call.

Production Failure Audit & Fixes

  • Incomplete data extraction: the agent read the customer's document but wasn't capturing a key eligibility field. Coverage rose from 2% to 91%, including 12 months of history so partners could decide on the average rather than a single month.
  • Customers rejected for no real reason: an entire segment was blocked when only one specific condition actually restricted that profile; a misreading identified customers from two regions as belonging to a supplier with suspended credit, wrongly blocking 34 customers; and a credit block stayed active even after its root cause was fixed, denying an already-approved high-value proposal.
  • 142 registrations silently stuck: when a lead gave only a first name, the partner required a full name and the proposal was never created, with no one asking for the missing data. Fixed by extracting the full name directly from the customer's document (printed on it) and, when missing, asking for it explicitly.
  • Agent communication: eliminated unconfirmed-cause promises, denials announced before the cause was known, excessive emoji use (risk of WhatsApp flagging as spam), and form-style questions. I also implemented a context-cleanup routine to stop the agent repeating incorrect information already fixed in the system but still present in the conversation history.

Business Findings

Testing the funnel with real customers, I identified a structural constraint: a specific customer profile is rejected by every partner in one segment, since their benefit doesn't stack with an equivalent government benefit, even though that profile is well accepted by the financial partner. Since a meaningful share of the base fits this profile, the real addressable market for that segment is much smaller than the raw numbers suggest, a finding brought to partner negotiations.

Problems I Solved

  • Dead webhook: an outcome webhook stopped being delivered for 4 days, freezing dozens of proposals in 'processing'. I traced it from symptom to root cause (logs, database state, polling) and built a systemd job doing active polling every 5 minutes, recovering 43 approved proposals and cutting the stuck backlog from 28 to 3 leads.
  • Race condition in human takeover: when an agent joined the conversation, the bot did not pause and both replied together. I fixed it with robust phone normalization and a state re-check immediately before sending, making human handoff safe.
  • OCR latency: I cut OCR plus routing-decision time from 8s to 3.2s with smart caching (TTL) and request batching.

Reliability, Infra & Security

  • systemd services with auto-restart, health checks, state-sync watchdogs, and automatic token renewal (auto-refresh before expiry).
  • Configurable network egress layer to ensure reliable delivery to external services with unstable connectivity, without coupling business logic to infrastructure.
  • Throttling with exponential backoff to respect rate limits and behave as a well-mannered client of partner services.
  • Sensitive data handling per LGPD: encryption at rest, HTTPS transmission with JWT, retention policy, and context isolation between leads.
  • Observability with structured logging (JSON), a real-time dashboard, and automatic alerts (Slack/Email) for VPS health and webhook failures.

Automated sales on WhatsApp: from 43% to ~89% of registrations completed

Work from my internship at F5 Tecnologia: find out, with production data, why the automated registration was failing, and fix the causes instead of the symptoms.

Context

A reseller for a pay-TV carrier sells plans on WhatsApp with a chatbot. The bot talks to the customer and collects the data, and a robot (Selenium) fills in the proposal on the carrier's portal: package, add-ons, registration, payment, and validation. When the registration fails, the sale stops and the customer is left without an answer.

The problem

The sales team raised four complaints:

  • the bot stopped at the registration step with many customers;
  • answers to off-script questions took a long time to arrive;
  • registration was slow;
  • proposals were redone several times for no apparent reason.

The share of registrations that became a proposal was 43%, and it dropped as low as 29% in October. After the fix, in November, it reached about 89%.

Diagnosis: measure before changing anything

I cross-checked three sources: the timestamped step-by-step log of every robot run, the API request log, and the message history of the conversations. Three findings came out of it:

  • Most failures had a single cause. A safety check blocked 44 of 54 registrations because it did not recognize the item selected on the screen: the screen had changed and the code had not kept up.
  • The slow answers were not the AI's fault. The model answered in ~1.5 s. The time went into a fixed 15 s wait window, meant to gather a customer's message sent in pieces, which applied even to complete questions.
  • The redone proposals came from an old rule. It re-drew security questions that no longer existed, and cost ~49 s per registration.

What was done

  • Registration. I fixed how the selected item is recognized and removed the obsolete re-draw. Silent redos are now capped at 1.
  • Adaptive wait window. A recognized question (price, channels, installation…) closes the wait in 4 s, a complete piece of data (ZIP code, CPF, email) in 8 s, and the overall ceiling went from 15 s to 8 s. The cutoff came from data: out of 4,078 messages, only 2% had a second message from the customer between 8 and 15 s later.
  • Number porting with a different area code. I reproduced the failure live on the portal and found that the line's area code came from the registration's mobile number, not from the address. The robot now adjusts the area code and, if the carrier refuses, moves on with a new number instead of getting stuck. In the chatbot, the customer now confirms the number they typed and is told when the porting cannot go through.
  • Add-ons by payment method. The item required by each payment method is now checked before the others, and a failure now saves full evidence (a screenshot and the list on the screen) for diagnosis.
