Estudo de caso · IAprovale

Achar o edital ou a vaga certa e não perder o prazo

Produto que eu construí e mantenho, em produção. O front-end é HTML, CSS e JavaScript puros, o backend é Python. Este texto descreve só o que está no repositório, no changelog e nas docs públicas.

O problema

  • Quem estuda para concurso precisa achar um edital aberto que combine com a formação, e a informação está espalhada em muitos sites.
  • Achar não basta: inscrições e provas têm data, e acompanhar isso à mão é fácil de errar.
  • Quem procura vaga tem uma necessidade parecida: saber se o currículo combina com o cargo antes de se candidatar.

O que eu construí

  • Busca de editais em linguagem natural, filtrada por formação e por estado.
  • Alertas e Acompanhando: a pessoa acompanha um concurso e recebe avisos sobre inscrições e provas.
  • Carreira e Empresas: envio de currículo (PDF, DOCX ou TXT), busca de vagas e, para cada cargo de um concurso acompanhado, um resultado de combina, combina em parte ou não combina, com o motivo e o que falta.
  • E-mail opcional, confirmado por código, com a Brevo como operadora de envio, para o resumo diário e os avisos da conta.

Decisões de engenharia

  • Front-end puro, sem CDN e sem bundler. HTML, CSS e JavaScript com Alpine.js na versão CSP. O Alpine e o pdf.js são servidos pelo próprio projeto, e a política de segurança de conteúdo deixou de permitir um servidor de scripts de terceiros.
  • Só Python no backend. Todo código novo de servidor é Python, o que deixa uma linguagem só para testar, publicar e manter.
  • Dados de usuários nunca vão para as ferramentas de desenvolvimento. O desenvolvimento usa só dados fictícios e cópias locais; dados de produção e segredos ficam fora dessas ferramentas.
  • Privacidade e termos versionados, com aceite. Cada mudança nos textos ganha uma versão, como a 1.3, que descreve o e-mail opcional, a Brevo como operadora e a transferência internacional correspondente.
  • Mensagens que dizem o que houve. Mensagens de erro e confirmação saem de um dicionário único, e as regiões de alerta ficam sempre na página para o leitor de tela anunciá-las.

Qualidade

CIlint do front-end a cada mudança no front-end
  • Testes e2e com Playwright contra uma API fictícia, nos temas claro e escuro, em 1280, 390 e 320 px.
  • Rótulos contêm o texto visível, alvos têm tamanho mínimo de toque e os pontos de quebra são padronizados.

O que eu aprendi

  • A acessibilidade achou bugs reais: rótulos cortados em 390 px, um alerta oculto que nunca era anunciado e foco caindo fora de um diálogo.
  • Menos dependências, menos surpresa: tirar a CDN fez os testes deixarem de baixar o Alpine e a política de segurança ficar mais estrita.
  • Privacidade é trabalho de projeto, não rodapé: decidir o que se guarda e por quanto tempo veio antes da tela.

O que não está pronto

  • Parte das mudanças mais recentes consta como não publicada no changelog (versão 3.13.0).
  • As verificações automáticas de acessibilidade não provam conformidade; alguns pontos só a tecnologia assistiva real confirma.
  • O produto não tem números de uso publicados, então este estudo não afirma nada sobre audiência.

Tecnologias

Python, FastAPI, PostgreSQL, DeepSeek, HTML, CSS, JavaScript, Alpine.js (CSP), pdf.js, Playwright, axe, GitHub Actions, Brevo, Caddy.
